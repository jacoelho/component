# Component architecture

This is the canonical record of the decisions that must stay true as the code
changes. The [README](README.md) is the user guide; the package documentation
is the API reference.

## Capability

`component` owns two things:

1. A typed build graph. Each node is declared by one call that names its
   inputs, its constructor and the hooks of the value it creates.
2. An `App`: one value per reachable node, built in dependency order, started
   in dependency order and stopped in reverse.

The application owns resource policy: what a constructor acquires, what a
start hook checks, how a task ends, what a drain hook does. The library does
not discover methods by name, look up values by type or string, install signal
handlers or add timeouts of its own.

## Files

| File | Owns |
|------|------|
| `ref.go` | `Ref`, `Root`, `In`, `Started`, `Value`, the immutable `node` and labels |
| `constructors_gen.go` | `Provide*` for no inputs and `Map*`, `MapValue*`, `MapContext*` for 1–8, generated by `internal/genconstructors`, which defines the three constructor shapes once. CI fails when the file is stale |
| `option.go` | hook options and the `Serve` adapter |
| `app.go` | `New`, `Start`, `Wait`, `Stop`, `Plan`, `Get`, `Replace` |
| `errors.go` | sentinels, `NodeError`, `PanicError` |

## Graph

- **Identity.** A `Ref[T]` identifies the node created by one call. Two calls
  with the same constructor create two nodes; nothing is deduplicated by type.
  `Ref` holds a phantom `[0]*typeMarker[T]`, so a `Ref[A]` cannot be converted
  to a `Ref[B]` even when `A` and `B` differ only in struct tags (a bare `*T`
  would allow that), and every `Ref` stays comparable.
- **Acyclic by construction.** A node can take only refs that already exist,
  so no cycle can be written. `New` does not check for cycles.
- **Edges come only from inputs.** The refs a constructor takes are its
  dependencies. There is no ordering-only edge: when order matters, the
  dependent takes the capability it uses (a `Submitter`, a ready client), so
  construction and lifetime share one edge.
- **Closed interfaces.** `Root` and `In` have unexported methods, so only
  `Ref`, `Started` and structs that embed a `Ref` satisfy them. `New` reports
  a nil pointer to such a struct as an invalid reference. `In[T]`'s method mentions `T`, which lets a
  `Ref[T]` argument infer `T`.
- **Owner declares hooks.** Options attach to the constructor call that
  creates a value. A consumer cannot change how a dependency stops.
- **Per-App state.** Nodes and options are immutable and shared by every
  `App` built from them. An option is stored as a function that produces its
  hooks once per `App`, so `Serve` keeps one listener per `App`.
- **Labels are diagnostics.** The default label is the constructor's function
  name without its import path (`storage.open`). Labels never act as keys and
  may repeat.

## Lifecycle

One rule orders everything: a node starts after all its dependencies and stops
before any of them. Nodes with no path between them have no guaranteed
relative order; the current order (first reach from the roots) is
deterministic but not part of the contract.

### State

Lifecycle state has three owners, all in `app.go`. Each is one enum that only
advances; no other field encodes lifecycle.

| State | Values | Guard | Changed by |
|-------|--------|-------|------------|
| `appState`, per App | `appBuilt` → `appStarting` → `appStarted`; `appBuilt` → `appFailed`; any → `appStopping` (final) | `mu` | `failBuild`, `beginStart`, `endStart`, `beginStop` |
| `nodeState`, per node | `nodePending` → `nodeBuilt` → `nodeBegun` | `op`, or `New` before the App is shared | `New` (a replaced node is born built), `build`, `startNode` |
| `exitClaim`, per App | `unclaimed` → `claimedByWait` or `claimedByStop` | `mu` | `reportExit`, `claimForStop` |

- `appState` decides what `Start`, `Get` and `Wait` return and whether a task
  exit is Wait's or Stop's to report. In `appFailed` all three return
  `ErrBuildFailed`: the values are partial and the App will never run. `stopStart` is set exactly while the
  state is `appStarting`, and `stopBegun` is closed by the move to
  `appStopping`.
- `nodeState` decides what Stop owes a node: nothing when pending, `OnClose`
  when built, and also `OnDrain` and `OnStop` when begun.
- There is no stopped state. Teardown runs once per App, so nothing needs to
  ask whether a node or the App has finished stopping.

Two smaller pieces of state stay where they are because they have one writer
and no policy: a task is running until its `done` channel closes, and `Serve`
holds its listener in a per-App closure from listen to shutdown.

### New

1. Collects every declaration error before any constructor runs: zero or nil
   refs, nil constructors or hooks, every zero or invalid option of a node,
   `Replace` of an unreachable or twice-replaced ref.
2. Orders the reachable nodes with an iterative depth-first walk, so build
   order is a topological order. Start uses it forward, Stop in reverse.
   `Plan` reports it; it is the start order except for nodes a `Started`
   input started earlier (step 3).
3. Builds each node once. A `Started(r)` input first starts `r` and its
   unstarted dependencies, in build order. A started node's dependencies have
   all started, so the walk stops there and total work stays O(V+E).
4. `Replace(r, v)` uses `v`, runs no hooks for `r`, and does not walk `r`'s
   inputs, so nodes reachable only through `r` are never built.
5. A constructor that fails or panics transfers nothing and must clean up its
   own partial work. `New` stops building and returns the error with the
   App in `appFailed`. It does not roll back, exactly like `Start`: `Stop` is
   the only teardown, so what was built or started is torn down under the
   caller's stop context, never under a build context that may be the reason
   for the failure.
6. `New` always returns a non-nil `App`, including for declaration errors,
   where the App has no nodes. Callers defer `Stop` before checking the error.

### Start

Runs nodes serially in build order: each node's `OnStart` hooks in option
order, then its `Go` tasks. A node is *begun* (`nodeBegun`) once its first hook
is about to run; this decides which teardown hooks apply. Tasks get one
context per node, made with `context.WithoutCancel(startCtx)` and cancelled
only at that node's turn in Stop. Start stops at the first failure or when its
context is done, does not roll back, and leaves cleanup to Stop. A hook
failure is a `*NodeError`; a cancellation between nodes is not, because no
node failed: it wraps the context's cause and names the node it stopped before.

### Wait

Returns the first task exit that happens before Stop begins (a nil return or
`runtime.Goexit` becomes `ErrExited`), `context.Cause` of its context, or
`ErrStopped` once Stop begins. Exits after Stop begins are Stop's to report.
The first exit is claimed under `mu` by whichever of Wait and Stop reports it
first, so Wait and Stop never both return it; every other task error goes to
Stop.

### Stop

1. **Drain:** `OnDrain` hooks of every node whose start began, in reverse
   build order, before anything else stops.
2. **Per node, reverse build order:** cancel its task context; run `OnStop`
   (only if its start began) and `OnClose` (always, for built nodes) in reverse
   option order; then wait for its tasks. Hooks run before the wait so that,
   for example, `Shutdown` is what makes `Serve` return.
3. **Failures:** Stop continues after every error, runs each hook at most once
   and never retries. Errors are joined, each in a `*NodeError` with label and
   phase. A task that returns its context's error after cancellation is a
   clean exit. A task error that `Wait` already returned is not repeated.
4. **Deadline:** once the stop context is done, Stop no longer waits (each
   task not yet finished is `ErrAbandoned`), still calls the remaining hooks
   with the expired context, and joins `ctx.Err()` when it abandoned a task.
   A task that is about to return when the deadline passes, such as `Serve`
   right after `Close`, is also reported abandoned. `Serve` then falls back from
   `Shutdown` to `Close`.
5. **Repeat calls:** `sync.Once`; concurrent and later callers wait for the
   first call and get its result.

`OnStop` pairs with start and `OnClose` pairs with construction. That is why a
node built but never started (for example when `Stop` follows a failed `New`)
is closed but not stopped or drained.

### Concurrency

- At most one constructor or hook runs at a time. Each task is one goroutine
  owned by the `App` and joined, or reported abandoned, in Stop.
- `op` serialises `Start` and Stop's teardown. Start registers its cancel
  function in the same step that enters `appStarting`, so a Stop either comes
  first and Start returns `ErrStopped`, or comes later and cancels it. A Stop
  issued during Start marks the App stopping at once (so `Get` and `Wait` see
  it), cancels Start's context with `ErrStopped` (so Start dispatches no
  further node), and tears down after the running hook returns. A hook that ignores its
  context therefore delays Stop past its deadline.
- Calling `Stop` or `Start` from a hook or task of the same App deadlocks:
  Start holds `op`, Stop's `sync.Once` is not re-entrant, and teardown waits
  for the calling task. A task asks for shutdown by returning; Wait reports
  it.
- `mu` guards `appState` and the first task exit. Values are written
  only during `New`, so `Get` reads them without locking.
- Panics in constructors, hooks and tasks are recovered into `*PanicError`.
  `runtime.Goexit` in a constructor or hook is not intercepted: it ends the
  calling goroutine, as it would without the library. In a task it is
  recorded as an `ErrExited` exit.

### Bounds

Build, ordering and the `Started` walks are O(V+E) in time and memory. The
walk is iterative, so graph depth is limited by memory, not stack. Every
deadline comes from a caller context. There are no retries, background
goroutines other than declared tasks, or queues.

## Errors

`NodeError{Err, Label, Phase}` wraps every build, start, task, drain, stop and
close failure of a node. `Phase` is a named type with one constant per phase;
`OnClose` failures are `PhaseClose`, `OnStop` failures and abandoned tasks are
`PhaseStop`. Sentinels classify:
`ErrInvalidDefinition`, `ErrInvalidReference`, `ErrBuildFailed`, `ErrStarted`, `ErrStopped`,
`ErrExited`, `ErrAbandoned`, `ErrPanic`. `PanicError` keeps the panic value and
stack, and unwraps to `ErrPanic` and, when the value is an error, to it.

## Rejected alternatives

| Alternative | Why rejected |
|-------------|--------------|
| Declared ordering edges beside plain wiring | A second source of truth: a forgotten edge compiles and misorders shutdown |
| Lifetime scopes ordered by registration | Order comes from call position, not the graph |
| Dynamic `Use(b, ref)` inside builders | Dependencies hide in builder bodies; a failed dependency forces a zero value, a `(T, error)` per use, or a panic through user code |
| One hook name over a union of function shapes | Go cannot infer `T` through a union constraint (`cannot infer T`) |
| A `Start`/`Stop` interface on `T` | Needs a wrapper type for every third-party resource |
| Keeping a failed stop pending and holding its dependencies | After an HTTP `Shutdown` timeout the database would never close |
| Reflection, type-keyed containers, consumer code generation | Moves validation from the compiler to runtime, or adds a build step |
| Package-level refs | Runtime configuration would need placeholders replaced at `New` |
| Parallel start and stop in v1 | No measured need yet. The order of unrelated nodes is unspecified, so a bounded `Parallel(n)` option can be added without breaking callers |
| `New` rolling back its own failure and returning a nil `App` | Teardown would run under the build context. When that context is why the build failed (a signal, a startup deadline), `OnStop` hooks get a dead context and tasks started through `Started` are abandoned with no `App` left to join them |
| A separate cleanup context option for `New` | A second teardown entry point and a second deadline source beside `Stop` |
| Building in `Start` so `New` never starts anything | Loses build-without-start, which `Replace` with `Get` relies on |
| Waiting for tasks before stop hooks | Deadlocks `Serve`, which returns only after `Shutdown` |

## Open questions

1. **Parallel start.** Mimir starts independent modules in parallel. Decide
   whether `Parallel(n)` ships before targeting such projects.
2. **Deliberately broken edges.** Prometheus serves its UI during WAL replay
   through a proxy that removes the web → storage edge. Document a pattern,
   such as a proxy node that owns the late binding.
3. **Large constructors.** Above eight inputs, a constructor takes one named
   input struct built by its own node, or the wiring package passes a struct
   of refs.
4. **Listener address.** `Serve` listens on `Addr`, so a caller using port 0
   cannot learn the bound port. Add a way to observe it if a caller needs one.
